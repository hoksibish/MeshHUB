# Milestone 1 — real MeshCore BLE evidence

## Baseline (2026-11-23 20:01 UTC)

- Branch `feature/m1-meshcore-ble` was created from `main` at merge commit `97434cde3cc07d5c710f606754302968e4b9c24e` after confirming M0 PR #2 was merged.
- Host: Omarchy Linux, Flutter 3.50.1, BlueZ 5.87; Bluetooth service active and one powered controller. This is **host** evidence, not Heltec evidence.
- `bluetoothctl --timeout 16 scan le` returned successfully (1,207 output lines). A locally filtered search found **zero** advertisements containing `MeshCore`, `Heltec`, or the documented `6e400001-b5a3-f393-e0a9-e50e24dcca9e` service. The known-device list had zero names matching `MeshCore` or `Heltec`. No device address or third-party advertisement is published here. The radio may be off, out of range, use a different name/advertisement, or not expose that UUID in its advertisements; this result alone cannot distinguish those cases.
- A second **MeshHub `bluez` 0.9.0 read-only scan** ran on 2026-11-24 UTC via `dart run tool/meshcore_ble_scan.dart`: `{"candidateCount":0,"serviceAdvertised":0,"nameHintOnly":0,"identityVerified":false,"paired":false,"connected":false}`. It used BlueZ D-Bus to scan LE advertisements without pairing/connecting and intentionally printed no BLE addresses or other nearby device details.
- A later scan on **2026-11-24 01:02 UTC** through MeshHub/BlueZ found **one fresh candidate** whose BlueZ-known UUID set contains the MeshCore service; its name has the MeshCore prefix. Read-only inspection reported `paired:false`, `connected:false`, `servicesResolved:false`, `firmwareRead:false`. The exact local device name/address/path are intentionally **not stored in this public repository**. Fresh observation plus service UUID is not yet proof that this is the owner's Heltec V3 or that it runs Companion 1.18.0. Owner confirmation and authenticated GATT/firmware readback remain necessary.
- The owner confirmed the candidate's name belongs to their Heltec V3. This confirms intended target selection, **not** firmware version or authenticated connection. A one-shot pairing attempt at **2026-11-24 01:06 UTC** (explicitly selected fresh candidate; no PIN accepted or logged) returned `BlueZAuthenticationFailedException`, leaving `paired:false`. Sanitized BlueZ journal entries reported `No agent available for request type 2` and `device_confirm_passkey: Operation not permitted`. A local interactive BlueZ pairing agent/OS dialog and owner confirmation of the on-device code are needed; do not guess a default PIN or transmit it in chat.
- At **2026-11-24 01:38 UTC**, `bluetoothctl info` read back `Paired:yes`, `Trusted:yes`, `Connected:yes`. A separate MeshHub BlueZ read showed `ServicesResolved:true`, one MeshCore service, and two characteristics: RX advertises `write`, TX advertises `read` and `notify`. BlueZ did **not** expose ESP32 MITM access permissions as characteristic flags; the transport was corrected to require the observed properties and successful pairing rather than nonexistent BlueZ flags.
- At **2026-11-24 01:41 UTC**, MeshHub opened the owner-confirmed, paired device through its real BlueZ transport, enabled TX notifications, sent only read-only `APP_START` and `DEVICE_QUERY`, and received both replies. The firmware reported protocol code **14**, model **Heltec V3**, firmware **`v1.18.0-81dbae5`**, build **`15-Oct-2026`**, and 40 channel slots. The BLE PIN and raw public key were not printed or stored; no message was sent or received over RF. BlueZ still reported `Paired:yes`/`Connected:yes` after the diagnostic closed. This proves a working authenticated GATT/Companion read-only handshake, **not** a second-endpoint message test or automatic reconnection.
- At **2026-11-24 01:44 UTC**, a third read-only handshake decoded the device-reported RF preset from `SELF_INFO`: **910,525 kHz** carrier (910.525 MHz), **62,500 Hz** bandwidth (62.5 kHz), **SF7**, **CR5**. This matches the earlier reported preset but does **not** establish regional/legal compliance, an available peer, or permission to transmit. No RF command was sent.

## Software preparation (not hardware acceptance)

- Field Test v0.1 adds a launchable Linux release (`run-field-test.sh`), real radio selection/read-only metadata in the app, a volatile real inbox with simulation off by default, bounded waiting-message drain, protocol-validated channel/direct send composer with explicit region/destination confirmation, count-only diagnostics, and retry on unexpected BLE loss. The send UI cannot establish region compliance or peer identity on its own; no test RF transmission was attempted.
- The live session uses the same selected-device BlueZ transport and Companion codec as the probe. It keeps full identity, raw frames and plaintext messages only in memory. Exact duplicate byte frames are suppressed for one process lifetime. Pairing still occurs only in the local OS, not the app. An interrupted send is reported uncertain and never replayed.
- At **2026-11-24 03:39:22–03:39:33 UTC**, a sanitized `meshcore_field_probe.dart` read-only baseline connected to the paired physical Heltec and verified Heltec V3, firmware `v1.18.0-81dbae5`, 910,525 kHz / 62,500 Hz / SF7 / CR5. The probe then deliberately disconnected **only the local BLE link**, observed one application reconnect attempt, re-established Companion readiness and reread the same firmware. It restored the initial OS connection on exit. It did not drain the radio queue or send RF. This is a **pass for one local BLE drop/recovery**, not out-of-range, reboot, Bluetooth off/on, BlueZ restart, or RF proof.
- Automated checks for this field-test build and the final release launch are recorded in `FIELD-TEST.md` and the checkpoint report; earlier counts of 23 domain / 22 app predate these changes.
